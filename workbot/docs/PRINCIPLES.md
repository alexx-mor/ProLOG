# Принцип работы WorkBot

## Назначение

WorkBot преобразует неструктурированные сообщения сотрудников в проверяемые
записи ежедневных работ. Его ключевая роль — сохранить первоисточник, извлечь
поля отчёта и передать результат в Excel, а в дальнейшем — в ProLOG.

## Общая схема

```text
Группа MAX
    │
    ▼
MAX Bot API
    │ message_created / message_edited
    ▼
Проверка типа чата и разрешённой группы
    │
    ▼
Сохранение исходного сообщения
    │
    ├─ строгий шаблон ───────────────► reports
    │
    └─ свободная форма ──────────────► historical_reports
                                         │
                                         ▼
                              Excel / будущий импорт ProLOG
```

## Этапы обработки сообщения

1. `runner.py` получает обновления MAX и сохраняет маркер Long Polling.
2. `service.py` отбрасывает неподдерживаемые события, сообщения самого бота и
   пустой текст.
3. Автор сохраняется в таблице `users`; группа — в `chats`.
4. Для групп проверяется `WORKBOT_ALLOWED_CHAT_IDS`, если список задан.
5. Исходное сообщение записывается в `messages`.
6. Идентификатор сообщения MAX используется как ключ идемпотентности.
7. Сначала запускается строгий парсер `parser.py`.
8. Если строгого отчёта нет, запускается `legacy_parser.py`.
9. Результат сохраняется в `reports` или `historical_reports`.
10. При редактировании сообщения старый результат заменяется новым.

## Почему исходный текст хранится всегда

Парсер со временем будет улучшаться. Сохранение `raw_text` позволяет:

- повторно разобрать старую историю;
- проверить, откуда появилось конкретное значение;
- исправить правила без повторного запроса данных у MAX;
- провести ручную проверку спорного результата;
- доказуемо связать запись ProLOG с первичным сообщением.

## Строгий и свободный форматы

Строгий парсер ожидает пять полей: дата, виды работ, затраченное время, объект
и местонахождение. Неполный шаблон помечается ошибкой.

Свободный парсер анализирует строки эвристически. Он умеет искать даты,
диапазоны дат, ФИО, интервалы времени, объект и местонахождение. Такой результат
не должен автоматически становиться окончательной записью ProLOG без проверки,
если сотрудник или объект определены неоднозначно.

## Идентификация сотрудника

Надежная идентификация не строится по имени профиля или username. Сотрудник
один раз выполняет `/register` в личном диалоге и передает контакт штатной
кнопкой MAX. WorkBot принимает номер только после проверки HMAC-подписи,
созданной MAX для токена бота.

ProLOG связывает `MAX user_id` с постоянным `Employees.id`, если подтвержденный
телефон встречается ровно в одной карточке сотрудника. Дубликаты, отсутствующие
телефоны и занятые привязки отправляются на ручную проверку. Отображаемое имя
MAX используется только как подсказка и аудиторский снимок.

## Контроль доступа

У WorkBot два разных контура доступа:

- сбор данных из разрешённых групп;
- управление в личном диалоге владельца.

Отправитель группового отчёта не получает права управления ботом. Команды и
кнопки проверяются по `WORKBOT_OWNER_IDS`. Это правило должно сохраняться и
после интеграции.

## Формирование Excel

Экспорт объединяет строгие и исторические отчёты, сортирует их по сотруднику и
дате, затем создаёт отдельный лист для каждой фамилии. Столбцы:

1. дата;
2. виды работ;
3. затраченное время;
4. объект;
5. местонахождение.

Excel является представлением данных, а не главным хранилищем. Главными
источниками остаются исходное сообщение и запись SQLite.

## Обработка ошибок и неоднозначностей

Правильная стратегия — не угадывать критические связи:

- неизвестный MAX ID направлять на привязку к сотруднику;
- неизвестный объект направлять на выбор из ProLOG;
- новую опечатку сохранять как предлагаемый алиас только после подтверждения;
- отсутствующее время оставлять пустым или нулевым с флагом проверки;
- не создавать дубликат при повторной доставке события MAX.

## Текущая модель хранения

| Таблица | Назначение |
|---|---|
| `bot_state` | Маркер Long Polling и служебное состояние |
| `users` | Профили MAX, подтвержденные телефоны и ручное ФИО |
| `chats` | Обнаруженные группы |
| `messages` | Исходные сообщения и статус разбора |
| `reports` | Один строгий отчёт на сообщение |
| `historical_reports` | Несколько извлечённых строк на сообщение |

Подробная схема находится в `workbot/storage.py`.

## Эксплуатационная модель

Текущий режим Long Polling подходит для пилота и локального тестирования.
Рабочая эксплуатация должна использовать:

- постоянно доступный процесс или сервис;
- автоматический перезапуск;
- ротацию логов;
- резервное копирование базы;
- новый рабочий токен;
- желательно Webhook MAX через HTTPS;
- мониторинг последнего успешно обработанного события.
