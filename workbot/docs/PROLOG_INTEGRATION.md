# Интеграция WorkBot с ProLOG

Этот документ предназначен для передачи разработчику ProLOG. Он описывает
текущее состояние WorkBot, рекомендуемую целевую архитектуру и порядок
реализации интеграции.

## Краткий контекст

WorkBot уже:

- получает сообщения и изменения сообщений из MAX;
- хранит первичный текст и идентификаторы MAX;
- разбирает строгие и свободные отчёты;
- знает автора и дату сообщения;
- формирует единый набор полей: сотрудник, дата, описание работ, часы, объект,
  местонахождение;
- импортировал старую историю рабочей группы;
- формирует Excel;
- имеет управление только для владельца.

WorkBot пока хранит данные в `data/workbot.sqlite3`. ProLOG хранит основные
данные в `data/prolog.sqlite3`. Автоматического обмена между базами нет.

## Соответствие данных

| WorkBot | ProLOG | Комментарий |
|---|---|---|
| `sender_id` / текстовое ФИО | `Employees.id` | Нужна постоянная таблица привязок |
| `work_date` | `WorkLogEntries.work_date` | Прямое соответствие |
| `work_types` | `WorkTypes.id` и `description` | В сообщении может быть несколько видов работ |
| `hours` | `WorkLogEntries.hours` | Должно поддерживать дробные часы |
| `object_name` | `Objects.id` | Нужны нормализация и подтверждённые алиасы |
| `location` | `Locations.id` | Аналогично объектам |
| `source_message_id` | отдельная таблица происхождения | Нужен ключ идемпотентности |
| `raw_text` | отдельная таблица импорта | Нужен аудит и повторный разбор |

## Обязательная предварительная правка

В БД ProLOG `WorkLogEntries.hours` имеет тип `REAL`, но модель
`models.WorkLogEntry.hours` объявлена как `int`, а
`WorkLogRepository._map()` выполняет `int(row["hours"] or 0)`.

Перед интеграцией необходимо:

1. изменить тип модели на `float`;
2. перестать приводить часы к `int` при чтении;
3. проверить ввод, таблицы, расчёты, аналитику и Excel ProLOG на значениях
   `7.5`, `0.5` и `10.25`;
4. добавить регрессионный тест на дробные часы.

Иначе отчёт WorkBot с 7,5 часа после чтения из ProLOG превратится в 7 часов.

## Рекомендуемая архитектура

На первом этапе не следует давать парсеру прямой бесконтрольный доступ к
`WorkLogEntries`. Между распознаванием и рабочим журналом нужен входящий
буфер с состояниями.

```text
MAX
 │
 ▼
WorkBot: raw message + parsed candidate
 │
 ▼
Импортный шлюз ProLOG
 │
 ├─ сотрудник найден?
 ├─ объект найден?
 ├─ местонахождение найдено?
 ├─ часы и дата корректны?
 └─ запись уже импортирована?
 │
 ├─ нет / неоднозначно ─► Очередь проверки в ProLOG
 │
 └─ всё подтверждено ───► WorkLogEntries
```

Рекомендуемый ближайший вариант — модуль импорта внутри репозитория ProLOG,
который читает WorkBot SQLite и записывает ProLOG SQLite через существующие
репозитории и транзакции. Это проще и безопаснее для пилота, чем немедленно
создавать сетевой API.

Для серверной эксплуатации лучше перейти к API: WorkBot на сервере отправляет
кандидаты в защищённый endpoint ProLOG или центрального сервиса, а настольное
приложение получает подтверждённые данные.

## Новые таблицы ProLOG

Названия можно скорректировать под стиль проекта, но смысл связей желательно
сохранить.

### `MaxUserBindings`

```sql
CREATE TABLE MaxUserBindings (
    max_user_id INTEGER PRIMARY KEY,
    employee_id INTEGER NOT NULL REFERENCES Employees(id),
    username_snapshot TEXT NOT NULL DEFAULT '',
    is_active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Связь должна быть `MAX user_id → Employees.id`. ФИО и username нужны только
для отображения и аудита. Изменение имени профиля MAX не должно разрывать
привязку.

Для исторических сообщений, где автор перечисляет нескольких работников,
желательна дополнительная таблица текстовых алиасов сотрудников:

```sql
CREATE TABLE EmployeeAliases (
    alias_normalized TEXT PRIMARY KEY,
    employee_id INTEGER NOT NULL REFERENCES Employees(id),
    original_alias TEXT NOT NULL,
    is_approved INTEGER NOT NULL DEFAULT 1
);
```

### `ObjectAliases`

```sql
CREATE TABLE ObjectAliases (
    alias_normalized TEXT PRIMARY KEY,
    object_id INTEGER NOT NULL REFERENCES Objects(id),
    original_alias TEXT NOT NULL,
    is_approved INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Пример подтверждённой связи:

```text
жимолово → Objects.id объекта «Жигалово»
```

Реестр объектов не нужно дублировать в WorkBot. Единственный источник истины —
таблица `Objects` ProLOG. WorkBot или импортный шлюз получает активные объекты
оттуда, а `ObjectAliases` хранит только варианты написания.

По тому же принципу можно добавить `LocationAliases` и, при необходимости,
`WorkTypeAliases`.

### `WorkBotImportRows`

```sql
CREATE TABLE WorkBotImportRows (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    max_message_id TEXT NOT NULL,
    source_index INTEGER NOT NULL DEFAULT 0,
    content_hash TEXT NOT NULL,
    raw_text TEXT NOT NULL,
    parsed_payload TEXT NOT NULL,
    confidence REAL NOT NULL DEFAULT 0,
    status TEXT NOT NULL,
    error_message TEXT NOT NULL DEFAULT '',
    worklog_entry_id INTEGER REFERENCES WorkLogEntries(id),
    imported_at TEXT NOT NULL DEFAULT '',
    updated_at TEXT NOT NULL,
    UNIQUE(max_message_id, source_index)
);
```

Предлагаемые статусы:

- `new`;
- `needs_employee`;
- `needs_object`;
- `needs_location`;
- `needs_hours`;
- `ready`;
- `imported`;
- `rejected`;
- `superseded`.

Эта таблица обеспечивает идемпотентность, аудит и повторную обработку после
редактирования исходного сообщения.

## Алгоритм сопоставления сотрудника

Порядок должен быть детерминированным:

1. Найти `max_user_id` в `MaxUserBindings`.
2. Проверить подписанный MAX телефон и точное совпадение с единственным
   `Employees.mobile_phone`; безопасное совпадение сохранить в `MaxUserBindings`.
3. Для перечисленного в тексте сотрудника проверить `EmployeeAliases`.
4. Попробовать точное нормализованное совпадение с `Employees.full_name`.
5. Если найден один кандидат по имени — только предложить его оператору.
6. Если кандидатов несколько или нет — оставить строку в очереди проверки.
7. После ручного подтверждения сохранить привязку или алиас.

Автоматически привязывать человека по похожему ФИО опасно. Доказательством для
первичной автопривязки служит только подписанный MAX контакт и уникальный номер
в справочнике сотрудников; затем главным идентификатором становится MAX ID.

## Алгоритм сопоставления объекта

1. Нормализовать ввод: регистр, `ё/е`, пробелы, кавычки, дефисы и служебные
   слова.
2. Проверить точное совпадение в `ObjectAliases`.
3. Проверить точное нормализованное совпадение в активных `Objects`.
4. Рассчитать похожесть с объектами и алиасами.
5. При высокой уверенности показать один предлагаемый объект.
6. При нескольких близких вариантах показать список выбора.
7. После подтверждения сохранить алиас для следующих сообщений.
8. Не создавать новый объект автоматически из текста сообщения.

Так явная опечатка «Жимолово» один раз подтверждается как «Жигалово», после
чего распознаётся стабильно. При переименовании объекта связь сохраняется через
`object_id`.

## Вид работ и описание

Сейчас `WorkLogEntries` содержит один `work_type_id`, но сообщение может
описывать несколько работ.

Для первого этапа рекомендуется:

- выбрать один основной `WorkTypes.id`, если он однозначно распознан;
- полный исходный перечень сохранить в `description`;
- не создавать новый вид работ автоматически.

Если ProLOG должен учитывать несколько типов одной записи отдельно, потребуется
таблица связи `WorkLogEntryWorkTypes(worklog_entry_id, work_type_id)` либо
разбиение отчёта на несколько записей с распределением часов. Это отдельное
бизнес-решение.

## Обработка изменения сообщения

MAX может прислать `message_edited`. Интеграция должна:

1. вычислить новый `content_hash`;
2. сравнить его с `WorkBotImportRows.content_hash`;
3. до импорта — заменить кандидата и повторить проверку;
4. после импорта — не менять табель молча;
5. создать состояние «изменено после импорта» и показать разницу оператору;
6. после подтверждения обновить связанную `WorkLogEntries`.

## Экран ProLOG «Входящие отчёты»

Минимально полезный интерфейс:

- фильтры по статусу, периоду и сотруднику;
- исходный текст MAX рядом с распознанными полями;
- выбор сотрудника, объекта, местонахождения и вида работ из справочников;
- подсветка отсутствующих и неоднозначных полей;
- кнопки «Подтвердить», «Отклонить», «Подтвердить и запомнить алиас»;
- массовое подтверждение полностью сопоставленных записей;
- ссылка на созданную запись журнала;
- отображение уверенности парсера и причины ошибки.

## Этапы реализации

### Этап 1. Контракт и точность данных

- Исправить дробные часы в модели ProLOG.
- Утвердить правила: один отчёт — одна запись или несколько записей.
- Утвердить поведение для отчёта без времени.
- Добавить миграции новых интеграционных таблиц.
- Добавить тестовую копию обеих баз.

Критерий готовности: ProLOG безопасно хранит 7,5 часа, схема создаётся на
существующей базе без потери данных.

### Этап 2. Справочники и привязки

- Реализовать `MaxUserBindings`.
- Реализовать алиасы сотрудников, объектов и местонахождений.
- Добавить управление привязками в интерфейс ProLOG.
- Использовать только `Employees.id`, `Objects.id` и `Locations.id` в
  подтверждённых связях.

Критерий готовности: выбранный MAX ID всегда приводит к одному сотруднику, а
«Жимолово» после подтверждения всегда приводит к объекту «Жигалово».

### Этап 3. Импортный шлюз

- Создать сервис чтения новых строк WorkBot.
- Записывать кандидатов в `WorkBotImportRows`.
- Реализовать уникальность `(max_message_id, source_index)`.
- Добавить режим `dry-run`, который ничего не пишет в `WorkLogEntries`.
- Логировать количество новых, готовых, спорных и повторных строк.

Критерий готовности: повторный запуск не создаёт дубликатов.

### Этап 4. Очередь проверки

- Добавить экран «Входящие отчёты».
- Реализовать ручное подтверждение связей.
- Сохранять подтверждённые алиасы.
- Записывать готовые строки через `WorkLogRepository`.

Критерий готовности: оператор может проследить путь от сообщения MAX до записи
ProLOG и исправить каждое распознанное поле.

### Этап 5. Обратная связь и контроль полноты

- Использовать производственный календарь ProLOG вместо простого правила
  «понедельник–пятница».
- Учитывать активность сотрудника и требуемые дни отчётности.
- Формировать список отсутствующих отчётов.
- Отправлять напоминание в нужную группу с упоминаниями MAX.
- Добавить настройку дня и времени напоминания.

Критерий готовности: напоминания не отправляются в выходные и не упоминают
неактивных или не обязанных отчитываться сотрудников.

### Этап 6. Рабочее развёртывание

- Перевыпустить тестовый токен.
- Перенести WorkBot на постоянно работающий сервер.
- Подключить HTTPS Webhook MAX либо управляемый сервис Long Polling.
- Настроить секреты через переменные окружения или хранилище секретов.
- Добавить резервные копии, мониторинг, ротацию логов и уведомление об ошибках.
- Ограничить сетевой API аутентификацией и журналированием.

Критерий готовности: перезапуск сервиса не теряет события и не создаёт
дубликаты.

## Рекомендуемые границы модулей

```text
workbot/
    max_client.py          # только транспорт MAX
    parser.py              # строгий разбор
    legacy_parser.py       # свободный разбор
    storage.py             # первичные сообщения и кандидаты

prolog/
    database.py            # миграции и репозитории
    integrations/
        workbot_import.py  # чтение кандидатов и идемпотентный импорт
        matching.py        # сотрудники, объекты, алиасы
    ui/
        workbot_inbox.py   # очередь ручной проверки
```

Фактический проект ProLOG пока не оформлен как пакет `prolog/`, поэтому новые
модули можно сначала разместить в корне и перенести позднее.

## Тесты, необходимые до включения синхронизации

- Дробные часы не округляются и не обрезаются.
- Повтор одного события MAX не создаёт вторую запись.
- Редактирование сообщения создаёт контролируемое обновление.
- Удалённый или неактивный объект не выбирается автоматически.
- Один MAX ID нельзя одновременно привязать к двум сотрудникам.
- Алиас объекта всегда ссылается на существующий `Objects.id`.
- Неоднозначное ФИО не импортируется автоматически.
- Ошибка одной строки не откатывает уже подтверждённые независимые строки.
- Импорт можно повторить после сбоя.
- В журнале сохраняется ссылка на исходное сообщение и исходный текст.

## Решения, которые нужно согласовать до разработки

1. Где будет постоянно работать WorkBot: на сервере или на рабочем компьютере.
2. Будет ли ProLOG локальным приложением с импортом или появится центральная
   серверная база/API.
3. Кто имеет право подтверждать алиасы и спорные отчёты.
4. Что делать с отсутствующими часами.
5. Как делить часы между несколькими видами работ.
6. Нужна ли синхронизация удаления сообщений MAX.
7. Какие сотрудники и календарные дни требуют обязательного отчёта.
