# ADR-001: Event-centric model

Статус: принято 09.08.2026

## Контекст

ProLOG регистрирует фактические работы сотрудников и в будущем будет хранить
наблюдения хода производства изделий. Сотрудник и изделие важны в разных
сценариях, но ни одна из этих сущностей не должна становиться универсальным
контейнером приложения.

Также необходимо различать сотрудника предприятия и пользователя системы.
Сотрудник может не иметь учетной записи, а пользователь может выполнять
операторские или административные действия, не являясь исполнителем работы.

## Решение

- Архитектура ProLOG остается event-centric.
- `WorkLogEntry` — типизированный факт труда сотрудника.
- `ProductionEvent` — отдельный типизированный факт хода производства изделия.
- Не создается универсальная EAV-таблица событий с JSON-полезной нагрузкой.
- `Employee` означает участника производственного процесса.
- `User/Actor` означает субъекта, совершившего действие в информационной системе.
- Связь Actor с Employee в будущем является отдельной необязательной связью, а
  не тождеством.
- Экраны сотрудника, изделия, объекта и аналитики являются read-моделями
  связанных фактов.

## Следствия

- Фото, стадия и процент готовности не добавляются в `WorkLogEntries`.
- Автор системного изменения хранится как Actor, исполнитель работы — как
  Employee.
- Для общего отображения допустима проекция временной шкалы, но не общая
  таблица хранения фактов.
- Production-модуль добавляется изолированно и не меняет смысл журнала работ.
