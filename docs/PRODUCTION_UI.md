# Ручное ведение хода производства

Статус: реализовано на этапе P6, ProLOG 0.6.0, core schema v4.

## Назначение

Карточка производства показывает связанные представления одного изделия:

- справочные свойства `Product`;
- текущее состояние, вычисленное из подтвержденных `ProductionEvent`;
- хронологию наблюдений и исправлений;
- `WorkLogEntry`, у которых указан данный `product_id`;
- фотографии из связей `ProductionEventAttachments`.

Карточка не хранит собственное состояние и после каждой операции заново читает
projection. `Products.readiness_percent` остается совместимым пересобираемым
снимком, а `Products.product_status` автоматически не меняется.

## Открытие карточки

В разделе **Настройки → Справочники → Изделия** выберите изделие и нажмите
**Производство**. То же действие доступно в контекстном меню строки. Обычный
редактор изделия продолжает изменять только его справочные свойства.

Карточка содержит четыре вкладки:

1. **Общие сведения** — объект, заводской номер, шифр, статус и даты изделия.
2. **Производство** — текущее состояние и временная шкала событий.
3. **Выполненные работы** — трудовые записи изделия и сумма человеко-часов.
4. **Фотографии** — агрегированная галерея вложений событий.

## Наблюдение

Действие **Добавить наблюдение** создает draft, связывает выбранные фотографии,
переводит событие в ready и подтверждает его одной пользовательской командой.
Этап, процент, описание и сообщивший сотрудник необязательны по отдельности, но
запись должна содержать хотя бы одно значимое наблюдение или фотографию.

Дата и время вводятся как локальные. На границе UI они переводятся в
timezone-aware UTC; при чтении выполняется обратное преобразование. Пустой
процент сохраняется как `NULL` и не копирует прежнюю готовность.

## Снижение, возврат и исправление

При снижении процента обычного наблюдения пользователь выбирает смысл:

- **Возврат / переработка** создает `rework` с обязательным описанием причины;
- **Текущее значение было ошибочным** открывает correction исходного события;
- **Новое наблюдение, снижение корректно** требует текстовую причину.

Correction всегда создает новый факт. Исходное подтвержденное событие становится
superseded только после успешного подтверждения исправления и остается видимым
в истории. Отмена формы не изменяет исходное событие.

## Фотографии

UI передает выбранные файлы в `AttachmentService`, а затем связывает полученные
Attachment с draft через `ProductionService`. Виджеты не вычисляют хэши, не
строят `storage_key` и не читают абсолютные пути. Просмотрщик получает
проверенные исходные bytes через сервис. Недоступный или поврежденный файл не
разрушает историю: пользователь видит placeholder, а подробность фиксируется в
журнале и attachment diagnostics.

Отмена после физического сохранения не запускает опасное каскадное удаление.
Metadata-backed Attachment может остаться без связи с событием до появления
отдельной утвержденной cleanup-policy.

## Actor и Employee

Текущая учетная запись ProLOG преобразуется в стабильный локальный `ActorRef`.
Actor создаёт и подтверждает запись. Поле **Сообщил сотрудник** независимо и
может ссылаться на Employee либо оставаться пустым. Идентичности не смешиваются.

## Ограничения P6

P6 не получает медиа из MAX, не использует WorkBot, не распознает текст, не
создает производственную аналитику и не добавляет планирование. Новых таблиц и
миграций в этом этапе нет.
