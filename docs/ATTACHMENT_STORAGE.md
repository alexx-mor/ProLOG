# Хранилище production-вложений

Статус: реализовано на этапе P3, ProLOG 0.5.10, core schema v3.

## Назначение

`Attachment` хранит метаданные конкретного полученного вложения в таблице
`Attachments`. Оригинальные байты хранятся вне SQLite в управляемом каталоге
attachment root. Несколько записей `Attachment` могут ссылаться на одно
физическое содержимое, но сохраняют собственные UID, имя и происхождение.

Этап P3 не связывает вложения с `ProductionEvent`, не принимает файлы из MAX и
не импортирует существующие фотографии.

## Корневой каталог

Portable-значение по умолчанию:

```text
data/attachments/
```

Путь можно переопределить полем `attachment_root` в `config.json`. Корень может
быть локальным или сетевым каталогом. В SQLite он не записывается, поэтому
перенос всего корня не требует изменения строк `Attachments`.

## Storage key

Формат ключа определяется SHA-256 исходных байтов:

```text
ab/cd/abcdef...64-hex-characters
```

Ключ всегда относительный, использует `/`, не содержит исходное имя файла и не
зависит от диска или компьютера. Абсолютные пути, drive/UNC-префиксы, `..` и
выход через symlink/junction за пределы корня отклоняются.

## Сохранение

1. Сервис вычисляет SHA-256 и определяет MIME, размер и геометрию изображения.
2. Store пишет оригинальные байты во временный файл внутри целевого каталога.
3. Выполняются `flush`, `fsync` и повторная проверка SHA-256.
4. Файл атомарно перемещается в content-addressed `storage_key`.
5. Только после готовности физического файла repository фиксирует metadata в
   транзакции SQLite.

Если содержимое уже существует, оно проверяется и повторно не записывается.
Другой источник может получить отдельную запись `Attachment` с тем же SHA-256.
Полная тройка `source_type + source_message_id + source_attachment_id`
идемпотентна: повторная доставка не создает новую запись.

Если запись файла не удалась, metadata не создается. Если файл сохранен, но
SQLite commit не состоялся, файл остается orphan и обнаруживается диагностикой.
Система не изображает общую ACID-транзакцию между SQLite и файловой системой.

## Диагностика и recovery

Структурированный отчет обнаруживает:

- metadata без файла;
- неверный SHA-256 физического файла;
- физический orphan;
- незавершенный временный файл;
- небезопасный `storage_key`;
- недоступный attachment root.

Диагностика ничего не исправляет и не удаляет автоматически. Подозрительное
незакрепленное содержимое можно переместить в `quarantine/`. Каскадное удаление
файлов до реализации ProductionEvent запрещено.

Recovery выполняется вручную после анализа структурированного отчета:

1. восстановить согласованную пару SQLite + attachment root из одной резервной
   точки;
2. запустить integrity, cross-database и attachment diagnostics;
3. не удалять orphan до проверки его происхождения;
4. поврежденный файл заменять только проверенной копией с тем же SHA-256.

## Резервное копирование

Единица production-backup:

```text
prolog.sqlite3 + полный attachment root
```

Одна SQLite-копия после появления вложений не является полноценной резервной
копией. Для согласованной копии необходимо остановить операции записи,
скопировать core DB и весь attachment root в одну именованную резервную точку,
затем проверить SQLite integrity и attachment diagnostics на копии.

Остальные component DB и WorkBot продолжают включаться в общий резервный набор
ProLOG по действующим правилам.
