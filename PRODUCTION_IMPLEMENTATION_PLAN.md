# План реализации production-модуля ProLOG

Статус: P0, P1, P2, P3, P4 и P5 завершены; production UI еще не реализован
Основание: `ARCHITECTURE_PROPOSAL.md` и ADR-001..ADR-006  
Версия ProLOG на момент первоначального планирования: 0.5.8
Текущая реализованная версия: 0.5.12

## 1. Границы плана

Production-модуль предназначен только для регистрации, структурирования и
анализа фактического хода производства изделий. Он не превращает ProLOG в ERP,
CRM, 1С, MRP или систему нормативного планирования.

Принятые ограничения:

- `WorkLogEntry` и `ProductionEvent` — разные типизированные факты;
- отдельный `production.sqlite3` не создается;
- `ProductionStage` и `WorkType` не объединяются;
- фотографии хранятся вне SQLite;
- `WorkBotImportRows` остается очередью только трудовых отчетов;
- парсер и AI не создают подтвержденные факты без установленного правила или
  решения оператора;
- Employee и User/Actor не смешиваются;
- существующие numeric ID сохраняются, для будущего API предусматриваются UID.

## 2. Правила выполнения этапов

Каждый шаг должен:

1. быть отдельной небольшой миграцией и/или изолированным модулем;
2. не менять поведение уже работающих экранов;
3. иметь автоматические тесты до подключения UI;
4. сохранять обратную совместимость с текущими базами;
5. проходить dry-run на копии рабочей базы;
6. обновлять `CHANGELOG.md` и версию схемы;
7. иметь критерий отката без удаления пользовательских данных.

Запрещен большой одновременный рефакторинг существующих `database.py`,
`services.py` и `ui/dialogs.py`. Новый домен создается в новых файлах.

## 3. Этап P0 — архитектурная стабилизация

Статус: завершен 09.08.2026.

Состав:

- версионированные `SchemaMigrations`;
- baseline всех текущих файлов ProLOG и WorkBot;
- блокировка более новой неизвестной схемы;
- диагностика версий;
- проверка межфайловых ссылок;
- ADR-001..ADR-006.

Этот этап не добавляет production-сущности и является обязательной точкой
перед следующими шагами.

## 4. Этап P1 — контракты production-домена

Статус: завершен 09.08.2026. Реализованы только чистые in-memory контракты;
таблицы, UI, файловое хранилище и интеграции не добавлялись.

### Изменения

- создать пакет `production/`;
- определить модели без SQL и UI:
  - `ProductionStage`;
  - `ProductionEvent`;
  - `Attachment`;
  - `ProductionInboxBundle`;
  - статусы и типы событий;
- определить отдельную модель `ActorRef`, не подменяя ей Employee;
- определить команды и запросы сервиса;
- зафиксировать правила времени в UTC и отображения в локальной зоне.

### Тесты

- процент допускает `NULL` или 0..100;
- подтвержденное событие требует изделие;
- Actor и Employee имеют разные поля идентичности;
- корректировка ссылается на существующее событие;
- доменный модуль не импортирует PySide6 или sqlite3.

### Критерий готовности

Доменные правила согласованы и тестируются в памяти. Таблицы и UI еще не
созданы.

Результат:

- модели, статусы, ActorRef и метаданные вложения находятся в `production/`;
- команды и запросы определены простыми типизированными структурами;
- все новые даты проверяются как timezone-aware UTC;
- readiness допускает `NULL` и целые значения 0..100;
- подтверждение и корректировка имеют явные доменные ограничения;
- пакет не зависит от SQLite, PySide6, WorkBot и файловой системы.

## 5. Этап P2 — справочник производственных этапов

Статус: завершен 09.08.2026.

### Миграция

Добавить в `prolog.sqlite3`:

- `ProductionStages(id, uid, code, name, sort_order, is_active, timestamps)`;
- уникальные ограничения по `uid` и `code`;
- начальный пустой справочник либо отдельно утвержденный seed.

Поскольку это новая сущность без legacy-строк, UID создается сразу при
добавлении записи.

### Сервис

- отдельные `ProductionStageRepository` и `ProductionStageService`;
- добавление, редактирование, включение/отключение, порядок;
- запрет удаления использованного этапа.

### UI

UI справочника подключается только после готовности репозитория и тестов. Он не
встраивается в универсальный `DirectoryItem`.

### Критерий готовности

Этапы существуют как самостоятельный справочник и не влияют на `WorkTypes`.

Результат:

- `ProductionStages` добавлена только в `prolog.sqlite3` миграцией schema v2;
- установлен редактируемый seed из 10 утвержденных этапов без `ASSEMBLY`;
- созданы отдельные `ProductionStageRepository` и `ProductionStageService`;
- добавлен отдельный UI-виджет в область справочников;
- code и UUID сохраняются при переименовании, UID не показывается в UI;
- отключение используется вместо физического удаления;
- `WorkType` не импортируется, не копируется и не синхронизируется;
- приложение и Windows EXE обновлены до версии 0.5.9.

## 6. Этап P3 — файловое хранилище вложений без MAX

Статус: завершен 09.08.2026.

### Миграция

Добавить метаданные `Attachments` в `prolog.sqlite3`. Файлы не добавляются в
SQLite.

### Инфраструктура

- интерфейс `AttachmentStore`;
- локальная реализация с относительными storage keys;
- атомарная запись через временный файл;
- SHA-256, MIME, размер и геометрия изображения;
- обнаружение отсутствующих и осиротевших файлов;
- запрет выхода пути за пределы настроенного корня;
- согласованное резервное копирование.

### Тесты

- повтор одной фотографии не создает второй физический файл;
- одинаковое содержимое сохраняет происхождение каждого вложения;
- сбой записи не оставляет готовую строку с отсутствующим файлом;
- перенос корневого каталога не меняет storage key;
- недопустимый путь отклоняется.

### Критерий готовности

Файл можно безопасно положить, проверить, прочитать и удалить из карантина без
production-событий и без WorkBot.

Результат:

- core schema v3 содержит только metadata-таблицу `Attachments`;
- оригиналы хранятся вне SQLite по относительному content-addressed ключу;
- `AttachmentStore`, `LocalAttachmentStore`, `AttachmentRepository` и
  `AttachmentService` разделяют filesystem, metadata и координацию;
- запись выполняется через временный файл, `flush`, `fsync`, проверку SHA-256 и
  атомарное перемещение до SQLite commit;
- одинаковые байты дедуплицируются физически, а происхождение вложений остается
  раздельным и повтор полной source-тройки идемпотентен;
- diagnostics обнаруживает missing, corrupt, orphan, temp, invalid key и
  недоступный root без автоматического удаления;
- корень задается конфигурацией, portable default — `data/attachments/`;
- backup/recovery описаны в `docs/ATTACHMENT_STORAGE.md`;
- приложение и Windows EXE обновляются до версии 0.5.10.

## 7. Этап P4 — хранилище ProductionEvent

Статус: завершен 09.08.2026.

### Миграция

Добавить:

- `ProductionEvents`;
- `ProductionEventAttachments`;
- `ProductionEventWorkLogs`;
- индексы по изделию, времени, этапу, статусу и источнику.

Таблицы создаются в `prolog.sqlite3`. Межфайловые ссылки на `Products` и
`Employees` проверяет production-сервис и общая диагностика.

### Правила

- новый факт получает `id INTEGER` и `uid UUID`;
- подтвержденное событие связано с существующим изделием;
- наблюдение может не иметь процента;
- процент не уменьшается без типа `rework` или явного подтверждения причины;
- исправление создает новое событие/ревизию;
- `reported_by_employee_id` не означает исполнителя работ;
- системное действие содержит Actor.

### Тесты

- создание, подтверждение, отклонение и корректировка;
- идемпотентный `idempotency_key`, при этом `source_ref` не уникален;
- запрет отсутствующего изделия;
- связи с несколькими фотографиями;
- необязательная многие-ко-многим связь с WorkLog;
- каскадное поведение не удаляет первичные факты.

### Критерий готовности

ProductionEvent полностью работает через сервис и репозиторий без UI и MAX.

Результат:

- core schema v4 содержит `ProductionEvents`, `ProductionEventAttachments` и
  `ProductionEventWorkLogs` с реальными FK внутри core;
- отдельные `ProductionEventRepository` и `ProductionService` реализуют
  создание, ready, confirmation, rejection, correction и явные связи;
- Actor сохраняется lossless snapshot полей ActorRef без подмены Employee;
- подтвержденные бизнес-поля и lifecycle дополнительно защищены SQLite-
  триггерами;
- correction подтверждается атомарно с переводом оригинала в `superseded`;
- readiness допускает correction/rework и требует сохраняемую причину для
  необъяснимого снижения observation;
- `object_id_snapshot` автоматически фиксируется из Product при confirmation;
- idempotency key различает безопасный повтор и конфликт payload;
- cross-database diagnostics проверяет Product, Object и Employee, а также
  внутренние production-связи;
- WorkLog deletion удаляет только relation row и не удаляет primary facts;
- Product legacy status/readiness, WorkBot, UI и physical attachments не
  изменяются;
- lifecycle и persistence описаны в `docs/PRODUCTION_EVENTS.md`;
- приложение и Windows EXE обновляются до версии 0.5.11.

## 8. Этап P5 — текущая проекция изделия

Статус: завершен 09.08.2026.

### Запросы

- временная шкала подтвержденных событий;
- последний этап;
- последний подтвержденный процент;
- дата последнего наблюдения;
- фотографии события;
- трудозатраты по изделию между событиями.

### Совместимость

Текущие `Products.product_status` и `readiness_percent` сохраняются. До
окончательного перехода они являются совместимым снимком и обновляются только
production-сервисом после подтвержденного события.

Legacy-процент остается явно маркированным `legacy_snapshot` до первого
effective confirmed события с readiness. Baseline автоматически не создается,
историческая дата не придумывается.

### Критерий готовности

Один запрос воспроизводит текущее состояние и полную цепочку, а расхождение
проекции диагностируется.

Результат:

- `ProductionProjectionService` строит состояние, timeline и интервалы труда
  только из индексированных запросов ProductionEvent и существующих данных;
- effective считаются только `confirmed`, а `superseded` остаются в timeline;
- поля этапа и готовности проецируются независимо в порядке
  `observed_at_utc`, `recorded_at_utc`, `id`;
- backdated, correction и rework пересчитывают историю без монотонного MAX;
- legacy readiness используется только как маркированный fallback;
- после confirmation синхронизируется только rebuildable readiness snapshot,
  а сбой синхронизации не отменяет подтвержденный факт;
- `product_status` не изменяется без утвержденного mapping;
- timeline возвращает Attachment metadata и explicit/manual WorkLog relations,
  не читая filesystem;
- интервалы WorkLog используют календарную границу `(previous, current]`, а
  одинаковый день помечается неоднозначным без искусственного распределения;
- persistent projection tables и schema migration не добавлялись;
- семантика описана в `docs/PRODUCT_PRODUCTION_PROJECTION.md`;
- приложение и Windows EXE обновляются до версии 0.5.12.

## 9. Этап P6 — ручной production UI

### Экран изделия

- паспорт существующего изделия;
- отдельная временная шкала событий;
- просмотр фотографий;
- ручное добавление этапа, описания и процента;
- явное подтверждение и корректировка.

### Ограничения

- файлы не читаются напрямую виджетом;
- WorkLog UI не получает поля производства;
- существующая навигация и экраны не меняют поведение.

### Критерий готовности

Историю изделия можно вести вручную без WorkBot. Это первая минимально полезная
production-функция.

## 10. Этап P7 — сохранение медиа в WorkBot

### Миграция WorkBot

Добавить:

- `message_revisions`;
- `message_attachments`;
- уникальность источника по message/revision/attachment ID.

### Изменения WorkBot

- сохранять конверт сообщения до проверки наличия текста;
- принимать сообщения только с фотографиями;
- сохранять исходный порядок;
- загружать файл с повторами и контролем хэша;
- не менять существующий текстовый парсер отчетов;
- не отправлять production-факты напрямую в журнал ProLOG.

### Тесты

- фото без текста;
- несколько фото в одном и разных сообщениях;
- редактирование подписи;
- повторная доставка;
- недоступный файл;
- перезапуск во время загрузки.

### Критерий готовности

WorkBot воспроизводит все исходные медиа и ревизии, но еще не группирует их в
производственные пакеты.

## 11. Этап P8 — транспорт WorkBot → production inbox

### Компоненты

- `integrations/workbot/production_source.py` читает WorkBot только через
  специализированный адаптер;
- `ProductionInboxBundles`, `ProductionInboxMessages` и
  `ProductionInboxAttachments` в `prolog.sqlite3`;
- копирование неизменяемого снимка источника;
- content hash и идемпотентность.

### Ограничения

- не использовать `WorkBotImportRows`;
- не создавать ProductionEvent;
- не создавать изделия автоматически;
- ошибка одного пакета не блокирует независимые пакеты.

### Критерий готовности

Повторная синхронизация не создает дубликаты, а изменение источника помечает
пакет как измененный.

## 12. Этап P9 — детерминированная группировка фото и текста

### Алгоритм

- ключ открытого пакета: chat ID + sender MAX ID;
- фото добавляются в порядке получения;
- следующий текст того же автора закрывает пакет в пределах временного окна;
- другой автор, новый день, тайм-аут или разделитель закрывают пакет на ручную
  проверку;
- текст не связывается задним числом через чужие сообщения;
- пакет без описания получает отдельный статус.

### Тестовый корпус

- одна фотография + описание;
- несколько фотографий + описание;
- два изделия последовательно;
- сообщения двух мастеров вперемешку;
- пауза/смена дня;
- удаление или редактирование текста;
- подпись внутри фото и отдельный текст.

### Критерий готовности

Группировка воспроизводима и объяснима; неоднозначные последовательности не
подтверждаются автоматически.

## 13. Этап P10 — сопоставление изделия, этапа и процента

### Порядок сопоставления изделия

1. точный заводской номер;
2. точный шифр/код;
3. подтвержденный `ProductAlias`;
4. нормализованное имя внутри установленного объекта;
5. ранжированные кандидаты без автоподтверждения.

### Извлечение

- процент извлекается отдельно от этапа;
- регистр и пробелы нормализуются;
- короткое имя учитывает контекст объекта;
- несколько изделий формируют предложения разбиения;
- версия правил и уверенность сохраняются.

### Критерий готовности

Парсер выдает предложения с объяснением источника совпадения и никогда не
создает подтвержденный факт самостоятельно.

## 14. Этап P11 — UI входящей производственной очереди

### Возможности

- исходная последовательность сообщений и фотографий;
- предложенное изделие, этап, процент и описание;
- выбор из существующих активных справочников;
- разбиение/объединение пакетов оператором;
- подтверждение, отклонение, отметка изменения;
- переход к карточке созданного события.

### Actor

Каждое решение сохраняет Actor текущей учетной записи. MAX-отправитель может
быть связан с Employee, но подтверждающий пользователь остается отдельной
сущностью.

### Критерий готовности

Каждый ProductionEvent раскрывается до решения оператора и исходных сообщений.

## 15. Этап P12 — production-аналитика

### Read-модели

- готовность по изделию и времени;
- длительность этапов;
- трудозатраты и число работников между событиями;
- стоимость по изделию/этапу/объекту;
- количество и полнота фотофиксаций;
- отклонения и возвраты на этап;
- качество автоматического распознавания.

### Историчность

До финансовой аналитики требуется версионирование ставок/назначений либо
снимок расчетного контекста WorkLog. Текущую ставку нельзя выдавать за ставку
прошлого периода.

### Критерий готовности

Любое агрегированное число раскрывается до ProductionEvent, WorkLog и
первичного источника.

## 16. Этап P13 — воспроизводимый научный датасет

### Состав

- неизменяемые исходники;
- подтвержденная разметка;
- версии правил/моделей;
- паспортные признаки изделия;
- последовательность этапов и процентов;
- трудозатраты и состав работников;
- метаданные изображений;
- исправления и причины.

### Перед началом

- добавить `WorkLogRevisions`;
- определить политику доступа и обезличивания;
- зафиксировать словарь признаков и целевых переменных;
- версионировать экспорт датасета;
- исключить утечку будущих данных в обучающие признаки.

### Критерий готовности

Один и тот же срез данных и версия преобразований дают одинаковый результат.

## 17. Этап P14 — AI-помощник

AI рассматривается только после накопления подтвержденной выборки.

Начальные задачи:

- предложить изделие;
- предложить этап;
- извлечь процент;
- предложить разбиение текста;
- выявить аномалию последовательности.

Обязательные данные результата:

- модель и версия;
- входной хэш;
- предложение;
- confidence;
- окончательное решение оператора;
- время обработки.

Автоподтверждение не включается без отдельного ADR, измеренных метрик и
безопасного режима отката.

## 18. Этап P15 — серверная версия и API RAMOR Software

Этот этап запускается только по критериям ADR-003.

### Идентичность

- API использует `uid`, а не локальный `id`;
- numeric ID остаются внутренними ключами локальной базы;
- Employee UID и Actor UID различны;
- при слиянии установок существующий UID не меняется.

### Контракты API

- идемпотентные команды с request ID;
- оптимистичная версия/ETag для корректировок;
- UTC timestamps;
- постраничные запросы событий;
- отдельный upload/download вложений;
- централизованный аудит Actor;
- обратная совместимость версий.

### Критерий готовности

Локальный и серверный репозитории проходят один набор контрактных тестов.

## 19. Порядок ближайших решений

После завершения этапа P0 рекомендуется реализовывать строго последовательно:

1. P1 — доменные контракты;
2. P2 — справочник этапов;
3. P3 — безопасное файловое хранилище;
4. P4 — ProductionEvent без UI;
5. P5 — проекции;
6. P6 — ручной UI.

Только после успешной ручной модели следует подключать WorkBot (P7–P11).
Аналитика, датасет и AI строятся после накопления подтвержденной истории, а не
параллельно с проектированием базовой сущности.
